# Специфікація вимог до системи паралельного пошуку

## 1. Призначення системи

Система призначена для побудови інвертованого індексу великого набору англомовних текстових документів і виконання пошуку за цим індексом. Побудова індексу має виконуватися паралельно з керованою кількістю потоків. Пошуковий запит може розширюватися мовною моделлю Ollama, після чого пошук виконується за ключовими словами через інвертований індекс.

Система має надавати:

- вебінтерфейс для побудови індексу, пошуку, перегляду результатів та етапів обробки запиту;
- REST API для перевірки стану, запуску індексації, пошуку та отримання статистики;
- WebSocket-інтерфейс для пошуку з передаванням проміжних етапів;
- консольний клієнт для виконання пошуку;
- засоби для дослідження продуктивності індексації та обробки запитів.

## 2. Технології та обмеження

- Сервер: C#, .NET 10, ASP.NET Core Minimal API.
- Вебінтерфейс: HTML, CSS, JavaScript.
- Консольний клієнт: C#.
- Тестування: xUnit.
- Запуск усієї системи: `docker compose up`.
- Ollama має працювати як окремий сервіс із моделлю `qwen2.5:0.5b`.
- Для розширення запиту сервер має звертатися до Ollama через `POST /api/generate`.
- Інвертований індекс має бути реалізований самостійно на основі масивів або списків.
- Використання готових потокобезпечних колекцій для структури індексу не допускається.
- Для паралельної індексації має використовуватися власний пул потоків зі змінюваною кількістю потоків.
- Для узгодження доступу до спільних даних дозволено використовувати стандартні механізми синхронізації C#.

## 3. Функціональні вимоги

### 3.1. Підготовка набору документів

1. Система має автоматично завантажувати англомовний набір даних QualC Gutenberg English Corpus із Hugging Face.
2. Завантажені дані мають автоматично перетворюватися на окремі текстові файли, придатні для індексації.
3. Підготовлені файли мають зберігатися локально та повторно використовуватися без повторного завантаження й перетворення.
4. Підготовлений набір має містити не менше 10 000 документів і мати загальний обсяг не менше 2 ГБ.

### 3.2. Побудова інвертованого індексу

1. Сервер має будувати інвертований індекс підготовлених текстових документів.
2. Побудова індексу має виконуватися паралельно власним пулом потоків.
3. Кількість робочих потоків має задаватися користувачем під час запуску індексації.
4. Спільна структура індексу має коректно синхронізуватися під час паралельного запису.
5. Після завершення індексації система має надавати статистику її виконання.

### 3.3. Пошук

1. Система має приймати текстовий пошуковий запит.
2. REST-пошук має підтримувати режим `keyword`.
3. У режимі `keyword` пошук має виконуватися за ключовими словами через побудований інвертований індекс.
4. Пошук через WebSocket має спочатку розширювати початковий запит за допомогою Ollama, а потім виконувати пошук за ключовими словами через інвертований індекс.
5. Результати мають містити знайдені документи у JSON-поданні.
6. Сервер має підтримувати одночасну обробку пошукових запитів кількох клієнтів.

### 3.4. Користувацькі клієнти

1. Вебінтерфейс має дозволяти задавати кількість потоків і запускати побудову індексу.
2. Вебінтерфейс має дозволяти вводити пошуковий запит і запускати пошук.
3. Вебінтерфейс має відображати знайдені результати.
4. Під час пошуку через WebSocket вебінтерфейс має відображати етапи `query_expansion`, `keyword_search` і `done`.
5. Консольний клієнт має дозволяти виконувати пошукові запити та відображати результати.

### 3.5. Дослідження продуктивності

1. Система має давати змогу виміряти та порівняти час побудови індексу для різної кількості потоків.
2. Система має давати змогу виміряти кількість оброблених пошукових запитів за секунду для різної кількості одночасних клієнтів.

## 4. Основні компоненти

- **Модуль підготовки даних** — завантажує QualC Gutenberg English Corpus, перетворює записи на текстові файли та зберігає їх для повторного використання.
- **Власний пул потоків** — розподіляє завдання індексації між заданою кількістю робочих потоків.
- **Інвертований індекс** — власна структура на основі масивів або списків, яка пов'язує ключові слова з документами.
- **Сервіс індексації** — читає документи, формує завдання та паралельно наповнює індекс.
- **Сервіс пошуку** — виконує пошук за ключовими словами в інвертованому індексі.
- **Інтеграція з Ollama** — надсилає запит моделі `qwen2.5:0.5b` через `/api/generate` для розширення пошукового запиту.
- **HTTP/WebSocket сервер** — реалізує REST API та канал `/ws/search`.
- **Вебінтерфейс** — керує індексацією і пошуком та відображає результати й етапи обробки.
- **Консольний клієнт** — виконує пошук через серверний API.
- **Тести xUnit** — перевіряють функціональність і коректність паралельної роботи.

## 5. API: формати запитів і відповідей

Усі REST-відповіді мають використовувати формат JSON. У наведених структурах назви полів визначають обов'язковий зміст відповіді; конкретні значення є прикладами.

### 5.1. Перевірка стану

`GET /api/health`

Запит не має параметрів.

Успішна відповідь:

```json
{
  "status": "ok",
  "ollama": true
}
```

- `status` — рядок зі значенням `ok`;
- `ollama` — значення типу boolean, яке вказує доступність сервісу Ollama.

### 5.2. Запуск індексації

`POST /api/index`

Тіло запиту:

```json
{
  "threads": 4
}
```

- `threads` — значення типу integer; додатна кількість потоків власного пулу.

Успішна відповідь після виконання індексації:

```json
{
  "status": "ok",
  "documents_indexed": 10000,
  "time_ms": 120000
}
```

- `status` — рядок зі значенням `ok`;
- `documents_indexed` — значення типу integer, кількість проіндексованих документів;
- `time_ms` — значення типу number, тривалість побудови індексу в мілісекундах.

### 5.3. Пошук через REST

`POST /api/search`

Тіло запиту:

```json
{
  "query": "parallel text search",
  "mode": "keyword"
}
```

- `query` — непорожній рядок типу string із пошуковим запитом;
- `mode` — рядок типу string; підтримуване значення: `keyword`.

Успішна відповідь:

```json
{
  "results": [
    {
      "doc_id": "document-00001",
      "score": 0.95,
      "snippet": "...parallel text search..."
    }
  ],
  "time_ms": 12.5
}
```

- `results` — масив об'єктів результатів пошуку;
- `doc_id` — рядок типу string з ідентифікатором документа;
- `score` — значення типу number з оцінкою відповідності документа запиту;
- `snippet` — рядок типу string із фрагментом знайденого документа;
- `time_ms` — значення типу number, тривалість пошуку в мілісекундах.

### 5.4. Статистика

`GET /api/stats`

Запит не має параметрів.

Успішна відповідь:

```json
{
  "documents": 10000,
  "index_build_time_ms": 120000,
  "threads_used": 4
}
```

- `documents` — значення типу integer, кількість проіндексованих документів;
- `index_build_time_ms` — значення типу number, тривалість побудови індексу в мілісекундах;
- `threads_used` — значення типу integer, кількість потоків, використаних для побудови індексу.

### 5.5. Пошук через WebSocket

Підключення: `/ws/search`.

Повідомлення клієнта:

```json
{
  "query": "parallel text search"
}
```

Сервер має послідовно передати повідомлення про такі етапи:

1. Розширення запиту:

```json
{
  "stage": "query_expansion",
  "data": {
    "original": "parallel text search",
    "expanded_terms": [
      "parallel",
      "concurrent",
      "text",
      "document",
      "search"
    ]
  }
}
```

- `stage` — рядок зі значенням `query_expansion`;
- `data.original` — рядок типу string із початковим запитом;
- `data.expanded_terms` — масив рядків із термінами, отриманими після розширення запиту.

2. Пошук за ключовими словами:

```json
{
  "stage": "keyword_search",
  "data": {
    "results": [
      {
        "doc_id": "document-00001",
        "score": 0.95,
        "snippet": "...parallel text search..."
      }
    ],
    "time_ms": 12.5
  }
}
```

- `stage` — рядок зі значенням `keyword_search`;
- `data.results` — масив результатів пошуку у форматі з полями `doc_id`, `score` і `snippet`;
- `data.time_ms` — значення типу number, тривалість пошуку в мілісекундах.

3. Завершення:

```json
{
  "stage": "done"
}
```

- `stage` — єдине поле повідомлення, рядок зі значенням `done`.

### 5.6. Помилки API

Для некоректного запиту або неможливості виконати операцію REST API має повертати відповідний HTTP-код і JSON:

```json
{
  "error": "Опис помилки"
}
```

WebSocket має передавати помилку як JSON-повідомлення:

```json
{
  "stage": "error",
  "error": "Опис помилки"
}
```

## 6. Нефункціональні вимоги

### 6.1. Продуктивність і масштаб даних

- Система має індексувати щонайменше 10 000 текстових документів загальним обсягом щонайменше 2 ГБ.
- Кількість потоків індексації має змінюватися без зміни програмного коду.
- Зібрані показники мають дозволяти порівнювати час індексації для різної кількості потоків.
- Зібрані показники мають дозволяти порівнювати пропускну здатність пошуку в запитах за секунду для різної кількості одночасних клієнтів.
- Сервер має одночасно обробляти пошукові запити кількох клієнтів.

### 6.2. Коректність паралельної роботи

- Паралельна індексація не повинна втрачати, дублювати або пошкоджувати дані через одночасний доступ.
- Результат індексації одного набору документів має бути функціонально однаковим за різної кількості потоків.
- Завершення роботи власного пулу потоків має гарантувати завершення всіх прийнятих завдань індексації.

### 6.3. Повторюваність і розгортання

- Усі компоненти системи мають запускатися командою `docker compose up`.
- Ollama та сервер застосунку мають працювати як окремі сервіси.
- Модель Ollama `qwen2.5:0.5b` має бути доступною сервісу пошуку.
- Уже підготовлений набір документів має повторно використовуватися між запусками.

### 6.4. Сумісність інтерфейсів

- REST API та WebSocket мають використовувати JSON для структурованих повідомлень.
- Вебінтерфейс і консольний клієнт мають працювати з однаковим серверним пошуком.

## 7. Критерії перевірки роботи

Система вважається такою, що відповідає вимогам, якщо виконуються всі наведені критерії:

1. Команда `docker compose up` запускає сервер застосунку й окремий сервіс Ollama з доступною моделлю `qwen2.5:0.5b`.
2. За відсутності локально підготовлених даних QualC Gutenberg English Corpus автоматично завантажується з Hugging Face і перетворюється на текстові файли.
3. Після підготовки даних наявні щонайменше 10 000 документів загальним обсягом щонайменше 2 ГБ; повторний запуск використовує збережені файли.
4. `GET /api/health` повертає JSON із `status` зі значенням `ok` і `ollama` типу boolean.
5. `POST /api/index` приймає `threads` типу integer, будує індекс і повертає `status` зі значенням `ok`, `documents_indexed` типу integer та `time_ms` типу number.
6. Індекс будується власним пулом потоків, а його структура реалізована на основі масивів або списків без готових потокобезпечних колекцій.
7. Для одного набору документів індексація з різною кількістю потоків дає однакові пошукові результати.
8. `POST /api/search` приймає `query` типу string та `mode` типу string зі значенням `keyword`, а у відповіді повертає масив `results` з полями `doc_id` типу string, `score` типу number і `snippet` типу string, а також `time_ms` типу number.
9. `GET /api/stats` повертає JSON із полями `documents` типу integer, `index_build_time_ms` типу number і `threads_used` типу integer.
10. `/ws/search` приймає `query`, використовує Ollama через `/api/generate` для його розширення і послідовно надсилає: `query_expansion` з `data.original` та масивом `data.expanded_terms`; `keyword_search` з масивом `data.results` і `data.time_ms`; `done`, що містить лише поле `stage`.
11. Вебінтерфейс дозволяє запустити індексацію, виконати пошук і переглянути результати та етапи WebSocket-пошуку.
12. Консольний клієнт виконує пошук через сервер і відображає результати.
13. xUnit-тести перевіряють побудову індексу, коректність паралельної індексації, пошук і формати API.
14. Експериментальні запуски дозволяють отримати час індексації для різної кількості потоків і кількість запитів за секунду для різної кількості одночасних клієнтів.
15. Сервер коректно обробляє одночасні пошукові запити кількох клієнтів.
